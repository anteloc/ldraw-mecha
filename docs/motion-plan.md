# Motion plan version 1

A plan is a JSON document with `version: 1`, an identifier `name`, `status`
(`draft` or `ready`), the unmodified inspection `source`, dictionaries `controls`,
`signals`, `bodies`, `anchors`, a `checks` list and explanatory `notes`.
`plan.validate` is the executable validator; `plan.evaluate` is the independent
kinematic evaluator. `plan --recipe ...` generates studied motion for specific
source selections; it does not imply every source mechanism is implemented.

The source manifest records path, hash, external-file dependency hashes, author,
section and all assembly/physical instance nodes. IDs such as `0/46/1` are
zero-based type-1 placement indices through the assembly tree. They identify an
occurrence, including repeats. They are valid only for that source revision and
selection. An embedded `.dat` is one physical part, not its internal primitives.

The following fields describe the studied 106 roof hinge with 75-degree outward
travel. For another hinge, remeasure the leaf ID, pivot, axis sign and limits;
keep the source manifest generated by the tool. All frames here are in the
selected source section, not in the part's or moving parent's coordinates:

```json
{
  "controls": {
    "open": {"default": 0, "min": 0, "max": 1.3089969389957472, "unit": "radian", "description": "Open the roof"}
  },
  "signals": {
    "lid_angle": {"expression": "clamp(a,0,1.3089969389957472)", "variables": {"a": "control:open"}}
  },
  "bodies": {
    "lid": {"instances": ["0/40"], "kind": "revolute", "origin": [0,-92,36],
            "axis": [-1,0,0], "signal": "lid_angle"}
  },
  "anchors": {},
  "checks": []
}
```

Each control has finite `default`, `min`, `max`, unit `radian|ldu|scalar` and a
description. Both the evaluator and Blender input drivers clamp inputs,
including keys outside the UI range. Unbounded rotation can use a deliberately large finite
range. Controls can be keyframed with ordinary Blender custom-property keys.

Signals have an `expression` and `variables` mapping local variable names to
`control:NAME` or `signal:NAME`. Dependencies are sorted, cycles rejected.
Supported syntax: numeric constants, `pi`, arithmetic `+ - * / ** %`, unary
signs, and `sin cos tan asin acos atan atan2 sqrt floor ceil min max abs pow
clamp`. Attribute access, imports, subscripts, comprehensions and arbitrary code
are rejected. Each expression is at most 255 characters for native Blender
drivers. Split long expressions into named intermediate signals. Names use ASCII
letters/digits/underscores, start with a letter and are at most 40 characters.

Useful signal relations:

| Mechanism | Relation | Required evidence |
| --- | --- | --- |
| Revolute joint | output angle = input angle | Pivot, axis, allowed range, moving group |
| External parallel gears | `-teeth_a/teeth_b * a` | Actual meshing, tooth counts, directed axes |
| Coaxial shaft coupling | `a` (or `-a` for reversed axis) | Rigid attachment, not just concentricity |
| Rack and pinion | pitch radius × pinion angle | Tooth pitch, slide axis, tangent sign |
| Symmetric differential | carrier = `(left+right)/2` | Equal side gears and consistent axes |
| Slider crank | `r*cos(a)+sqrt(L*L-r*r*sin(a)**2)-rest` | Crank radius, rod length, bank, phase |

`math3d.signed_gear_ratio` and `rack_ratio` reproduce the studied F1 contact sign
calculation. They do not automatically establish a gear mesh. The 42000 recipe
includes the exact tie-rod circle-intersection solution with a fixed source-pose
branch; generic branch switching or arbitrary loop solving is not implemented.

A body owns nonempty physical-leaf `instances` exactly once. `kind` is
`revolute`, `prismatic`, `fixed`, `rod` or `stretch`; every body has `origin` and nonzero
`axis`, with optional nonparallel `x_hint`. The adapter aligns local Z to that
axis. Revolute/prismatic bodies reference a signal; positive values rotate by
the right-hand rule or translate along the axis. A `parent` body composes
relative motion; joint origins still use the global rest frame.

A rod uses `start` and `end` anchor names and `x_hint`, with its local Y pointing
from start to end at rest. Anchors contain `body` and a source-rest `point`.
The rod copies the start position, aims local Y at the end, and takes local Z
from the declared `axis` projected perpendicular to Y. This supports spatial
links as well as planar rods; it never stretches to disguise a bad linkage.
Rods cannot parent or anchor other bodies. Add a check for each length:

```json
{"kind":"distance", "name":"tie_rod", "a":"rack_ball", "b":"knuckle_ball", "length":160, "tolerance":0.02}
```

`stretch` is reserved for flexible coil springs, the one physical part that
does deform. Its signal is a positive scale factor along the declared axis,
about `origin` (for example `(free_length + extension) / free_length` with the
origin on one spring seat); perpendicular dimensions are unchanged. Blender
drives the pivot's local Z scale. A stretch body cannot parent other bodies or
carry anchors, so no rigid part inherits the deformation. Put the spring under
the part that carries its fixed seat and check the moving seat separately (for
a shock absorber, against the piston rod). It does not relax the rod rule.
Shortcut parts such as a complete shock absorber are one mesh; split them into
their official sub-parts first (`scripts/split_shortcuts.py`).

Verification checks expression domains, finite results, dependency cycles,
double ownership, source freshness and declared closure. `sweep` varies one
control at a time. `check` combines that sweep with default/mixed poses and a
scope audit; add mechanism-specific coupled/asymmetric cases with `check --set`,
`evaluate` or Python. These workflow conveniences do not change the plan format.
The Blender verifier compares every moving part's evaluated matrix with the
portable evaluator, checks static parts, driver validity and link lengths.
These checks do not establish clearance or physical feasibility by themselves.

Coordinate conversion: the GLB exporter keeps LDraw node transforms, rotates the
root by pi around X and applies `0.0004` metres/LDU. Blender's glTF basis change
is `C(x,y,z)=(x,-z,y)`. Part matrices use `C M C^-1`; joint frames use `C F`.
The root owns scale. Joint calculations never mix metres with LDU.

GLB binding preserves existing extras and adds `mecha_id`, `mecha_source` and
`mecha_section`. It verifies reference, parent occurrence, colour and transform
before tagging. Exact duplicate placements (same parent, reference, colour and
matrix) are interchangeable and bind in source order; the conversion report lists
them. Library primitives placed directly as leaves (`p/`, e.g. LDCad rope
segments) are merged by the exporter into their parent's single mesh; those
occurrences share that node, tagged `mecha_merged`, rest in the parent's frame
and can only move as one body. Blender preflight also checks source-rest transforms.
`verify` compares matrices to 0.002 LDU by default; very large models can exceed
that through float32 rounding of deep placements (42110: up to 0.004 LDU at about
0.4 m from the origin), so `rig`, `apply_plan.py` and `check_lifecycle.py` accept
an explicit, reported `--tolerance`. Rebuild
and removal operate on the explicit root and restore each part's original
parent, parent inverse and basis. Unrelated rigs remain separate.

## Optional mechanism views and connection evidence

Optional `mechanisms`, `connections` and informational `discovery` fields record
evidence and scope in the same version-1 plan. Plans without them remain valid.
The validator checks graph references, while motion comes exclusively from
controls, signals, bodies, anchors and checks.

`connections` maps stable connection IDs to `a` and `b` physical occurrence IDs,
`kind` (`contact|coaxial|gear_mesh|worm_mesh|surface_contact|fixed|revolute|prismatic|ball|unknown`),
`status` (`candidate|reviewed|rejected`), nonempty `evidence`, and optional
`measurements`. Reviewed/rejected entries require a nonempty `review` note.
These are evidence records, not executable joints. Rejecting an edge retains
its evidence but hides it from diagrams. Connection graphs may contain loops.
`worm_mesh` measurements include an unsigned `wheel_per_worm_magnitude`; direction
must be reviewed before authoring signals. `surface_contact` is an agent-recorded
geometric/visual hypothesis (for example a crank bearing on a beam). Discovery
does not generate it from missing connector data. Neither kind executes motion.

`mechanisms` maps names to `label`, `parts`, `bodies`, `inputs`, `outputs` and
`notes`. The latter five are lists of strings. `parts` references physical IDs;
`bodies` references canonical bodies and expands to their parts. Inputs/outputs
use `part:ID`, `body:NAME` or `control:NAME`; part/body targets must belong to the
view. All planned bodies must appear in a view. Views may overlap; body ownership
remains unique. Shared occurrences and connections across view boundaries refer
to the same global objects, including when displayed as external nodes.

Views optionally declare `disposition: unresolved|planned|deferred|static`
(default `unresolved`). All other dispositions require a nonempty `review`
string. `planned` requires body references; `audit` also checks for a controlled
body. It means motion has been declared, not tested or physically proven.
`deferred` records a known omitted mechanism and why; `static` explains a reviewed
nonmoving/false-positive candidate. A view may include fixed supports alongside
moving parts. `audit PLAN --require-reviewed` fails for unresolved views, discovered
mechanical parts removed from all views, or planned views without a control.
It does not fail merely because an explicitly deferred mechanism remains.
The report always lists those deferrals. A plan's `ready` flag remains about its
declared motion; it does not assert every source mechanism was found or rigged.

Optional diagnostic Mermaid part views derive typed edges from `connections`.
Motion views derive joint frames, rod endpoints and control propagation from executable fields,
avoiding duplicate joint definitions. Changing a body's axis changes its next
diagram and Blender rig. A reviewed evidence edge alone does not change motion.
The index records the complete plan digest for freshness checks. These exports
do not reconstruct couplings from signal equations or establish graph/motion
equivalence. They are not the [curated references](reference/README.md), which
document selected working implementations after reviewing their evidence.
See [the workflow](workflow.md) for preparation and authoring.
